`Job` und `JobEvent` als `OCP\AppFramework\Db\Entity` mit Feldern nach SKELETON (camelCase, `addType` für int/bigint). Zusätzlich typisierte Helfer `getStatusEnum(): Status`, `getReasonEnum(): ?Reason`, die bei unbekanntem Wert eine `\UnexpectedValueException` mit statischem Text werfen (DB-Inhalt außerhalb der Liste ist ein Fehler, nie stilles Durchreichen).

`JobMapper extends QBMapper` mit `ITimeFactory $time` im Konstruktor (einzige Uhr) und Konstanten `LEASE_ANALYZE = 120`, `LEASE_APPLY = 300`, `LEASE_PURGE = 60`, `MAX_ATTEMPTS = 3` (Kommentar "vorläufig, Phase 8 setzt Werte nach Messung"). Methoden:
- `enqueue(int $fileId, string $uid, string $etag, Mode $mode, Lang $lang): Job` (status queued, task analyze, stage waiting, attempts 0, lease 0, Zeiten aus `$time`).
- `findOpenFor(int $fileId, string $uid, string $etag): ?Job` (Status `isOpen()`, für Idempotenz, Pitfall K).
- `findOpenByFile(int $fileId): Job[]` (für Listener).
- `ensureSlot(): void` (Insert id 1, `\OCP\DB\Exception` mit Grund `REASON_UNIQUE_CONSTRAINT_VIOLATION` schlucken).
- `claimNext(): ?array{job: Job, token: string, lease: int}`: (1) `purge`-Kandidaten zuerst und ohne Sperrzeile (bedingte UPDATE auf die Jobzeile mit `lease_until <= now`); (2) sonst Sperrzeile per `update('pii_slot')->set(job_id, claim_token, lease_until)->where(id = 1)->andWhere(lease_until <= now)`, `executeStatement() === 1` heißt gewonnen; (3) Kandidat: `task = apply` mit Status `approved` vor `task = analyze` mit Status `queued`, dann abgelaufene Leases mit Status `analyzing`/`applying`, FIFO nach `id`; Kandidat mit `attempts >= MAX_ATTEMPTS` wird `failed` mit Grund `repeatedly_stuck` und `task = purge` gesetzt und übersprungen; (4) bedingte UPDATE der Jobzeile mit wiederholter Frei-Bedingung, `claim_token = bin2hex(random_bytes(16))`, `lease_until = now + Lease`, `attempts = attempts + 1` über `createFunction`, Status `analyzing` bzw. `applying`, Stufe `waiting`; (5) Token zurücklesen; bei Verlust Sperrzeile freigeben und null. Keine Unterabfrage auf dieselbe Tabelle, kein `FOR UPDATE`.
- `extendLease(Job $job, string $token): bool` (Job und Sperrzeile, nur bei passendem Token und Lease in der Zukunft).
- `release(Job $job, string $token): void` (Sperrzeile frei: `job_id` null, `lease_until = 0`, nur wenn `claim_token` passt; Jobzeile `claim_token` null, `lease_until = 0`).
- `ahead(Job $job): int`: Zahl `queued`-Zeilen mit `task = analyze` und kleinerer `id`, plus 1, wenn die Sperrzeile einen gültigen Lease für einen anderen Auftrag hat.
`JobEventMapper::record(int $jobId, string $uid, string $action): void` mit `action` nur aus `Status`/`Subject`-Werten oder `placeholder_requested` (sonst `\InvalidArgumentException`).

`QueueMapperTest` (phpunit gegen die echte Testdatenbank des Servers wie FIN-Mapper-Tests, `ITimeFactory` gemockt): zwei wartende Aufträge, `claimNext` zweimal ergibt genau einen Auftrag und dann null; nach Ablauf (Uhr vorstellen) ist er wieder frei und `attempts` steigt; dritte Ausgabe ohne ack ergibt `failed(repeatedly_stuck)`; `apply` vor `analyze`; `purge` läuft trotz belegter Sperrzeile; `release` mit fremdem Token ändert nichts; `ahead` zählt 0, 1, 2 korrekt; `findOpenFor` liefert denselben Auftrag bei gleichem Etag und keinen bei anderem Etag.
